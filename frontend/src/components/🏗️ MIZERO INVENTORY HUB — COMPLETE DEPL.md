- Stock Adjustments (increase/decrease)
- Borrowing & Returns System

- Damage & Loss Liabilities (50%/100% replacement cost)
- Budget Tracking & Reports
- Supplier Management
- Department & User Management
- Activity Logs & Notifications
- Dashboard with Charts & KPIs
- CSV Import/Export
- PDF Receipt Generation (borrowings)
- Database Backup & Restore
Main Workflows
1. User logs in → JWT issued → SPA renders role-based UI
2. Staff requests stock → Admin/Manager approves → Stock-Out issued
3. Inventory received → Stock-In recorded → AVCO recalculated
4. Items borrowed → PDF receipt generated → Overdue cron checks daily
5. Items damaged/lost → Liability created (50%/100%) → Payments tracked
6. Monthly reports generated on stock movements, COGS, budget usage

Super Admin Protections (Unique Security Feature)
- Only one Super Admin account allowed system-wide
- Super Admin cannot be deactivated, deleted, or have role changed
- Super Admin cannot have department restrictions
- Only the Super Admin themself can change their own password
- All violations are logged to  super_admin_audit_log  table
HTTPS / Reverse Proxy Requirements
- HTTPS is REQUIRED in production for JWT + CSRF cookies to be secure
- Nginx reverse proxy handles SSL termination
-  trust proxy  is set to  1  in Express
- HSTS header is configured in nginx.conf (max-age=31536000)

Docker Compose Network Architecture
Internet → [Host Port 80]
               ↓
       [Frontend Nginx]  ← container: mizero-frontend
               ↓ (proxy_pass http://backend:5000)
       [Backend Express]  ← container: mizero-backend
               ↓ (mysql2 connection)
       [MySQL 8.0]        ← container: mizero-db
All three containers are on the  mizero-network  bridge network. Only frontend port 80 is exposed to the host. Backend and database are internal only.
API Communication
- Dev: Frontend Vite dev server proxies  /api/*  →  http://localhost:5000 
- Production: Nginx reverse proxies  /api/*  →  http://backend:5000 
- Websockets: Not used
- Health check:  /api/health  →  { status: 'ok', timestamp: '...' }

12. SCALABILITY ANALYSIS
Current Architecture Limitations
- Single server — All services on one Docker host; no horizontal scaling
- In-memory lockout — Login attempt tracking is per-process; multi-instance requires Redis
- Local file storage — Uploads and backups tied to local disk
- No caching — No Redis/Memcached for dashboard queries or API responses
- MySQL single-node — No read replicas, no sharding
